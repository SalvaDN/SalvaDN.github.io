Reto Talion — detección anti-VM y evasión de sandbox con Check-VM (Nishang)

Categoría: DFIR / Threat Hunting Sistema: Windows (Microsoft-Windows-PowerShell/Operational) Herramientas: EvtxECmd, Timeline Explorer, Hayabusa

Resumen

El reto Talion entrega artefactos de ejecución de PowerShell (.evtx) de un equipo donde se sospecha actividad maliciosa. El análisis identifica la ejecución de un mecanismo de fingerprinting y evasión de análisis basado en el framework Nishang (módulo Check-VM). El código evalúa parámetros físicos reales del sistema — incluyendo la presencia de sensores de temperatura ACPI vía WMI, cadenas de BIOS y controladores del kernel — para decidir si el entorno es un hipervisor antes de liberar etapas posteriores del ataque. Es una técnica clásica de pre-ejecución defensiva por parte del atacante: si detecta que está siendo analizado en una sandbox, se comporta de forma inocua o simplemente no continúa.

Escenario

El objetivo del reto es reconstruir, a partir únicamente de los logs de PowerShell, qué hizo exactamente el script ejecutado, cómo decide si está en una máquina virtual o física, y qué tácticas de MITRE ATT&CK cubre esa actividad — sin tener acceso al binario original, solo a lo que quedó registrado en Windows Event Log.

Artefactos y herramientas

  • Microsoft-Windows-PowerShell%4Operational.evtx — Script Block Logging (Event ID 4104) y ejecución de pipeline (4103 / 800)
  • EvtxECmd — parseo de los .evtx a CSV/JSON estructurado
  • Timeline Explorer — filtrado y correlación temporal de los eventos parseados
  • Hayabusa — caza de amenazas con reglas Sigma sobre el dataset

Concepto: ¿qué es la evasión de sandbox/VM y por qué importa?

Cuando una muestra maliciosa se ejecuta en un entorno de análisis automatizado (Cuckoo Sandbox, CAPE, Joe Sandbox, un EDR con detonación en sandbox, etc.), ese entorno casi siempre corre dentro de una máquina virtual. Un atacante que quiere evitar ser detectado puede hacer que su malware se pregunte, nada más arrancar, "¿estoy en una VM?" y, si la respuesta es sí, abortar o comportarse de forma completamente benigna. Esto se llama anti-VM o sandbox evasion, y es distinto de ofuscar el código: no esconde lo que hace el malware, decide cuándo mostrarlo. La parte interesante desde el punto de vista forense es que, precisamente porque el chequeo tiene que ejecutarse siempre (incluso en la máquina real de la víctima), deja rastro en los logs igual que cualquier otro comando — y ese rastro es lo que se analiza aquí.

Concepto: Script Block Logging y los Event ID 4104 / 4103 / 800

PowerShell puede registrar, en el canal Microsoft-Windows-PowerShell/Operational, no solo que se ejecutó un comando sino el contenido completo del código que corrió, incluso si llegó ofuscado o codificado en Base64. Los identificadores clave son:

  • Event ID 4104 (Script Block Logging): vuelca el bloque de script completo tal y como lo ve el motor de PowerShell, después de cualquier decodificación. Es la fuente más rica: aquí es donde aparece literalmente la función Check-VM completa, aunque se haya lanzado con -EncodedCommand.
  • Event ID 4103 (Module Logging) / 800: registra la ejecución de cada pipeline (cada comando o cmdlet invocado) junto con sus parámetros y, en muchos casos, la salida que produjo por Out-Default. Es lo que permite ver, por ejemplo, que se llamó a Get-ChildItem -Path "HKLM:\SYSTEM\ControlSet001\Services" y qué imprimió el script después.

La combinación de ambos permite reconstruir no solo qué código existía (4104) sino qué hizo de verdad en ese sistema concreto (4103/800) — una distinción importante en DFIR, porque un script puede contener lógica para detectar varios hipervisores distintos sin que todas esas ramas lleguen a ejecutarse.

Análisis técnico del código recuperado

El bloque de script recuperado vía Event ID 4104 es la función Check-VM del framework Nishang (una colección de scripts de PowerShell orientada a post-explotación), que a su vez reconoce basarse en el módulo checkvm.rb de Metasploit:

function Check-VM { 
<# .SYNOPSIS Nishang script which detects whether it is in a known virtual machine. 
.DESCRIPTION This script uses known parameters or 'fingerprints' of Hyper-V, VMWare, Virtual PC, Virtual Box, Xen and QEMU for detecting the environment. 
.NOTES The script draws heavily from checkvm.rb post module from msf. #> 
[CmdletBinding()] Param() 
$ErrorActionPreference = "SilentlyContinue" 

# --- CHEQUEO TÉRMICO / ACPI (Detección de Hardware Físico vs Virtual) ---
# Las sandboxes y máquinas virtuales habitualmente NO emulan sensores de temperatura ACPI.
$thermal = Get-WmiObject -Namespace root\wmi -Class MSAcpi_ThermalZoneTemperature
if ($thermal -eq $null) {
    # Ausencia de sensores térmicos física = Entorno Virtualizado / Sandbox
    $isVirtualThermal = $true
}

# --- PRUEBAS DE HIPERVISOR POR REGISTRO Y SERVICIOS ---
# Hyper-V Check Logic
$hyperv = Get-ChildItem HKLM:\SOFTWARE\Microsoft 
if (($hyperv -match "Hyper-V") -or ($hyperv -match "VirtualMachine")) { $hypervm = $true } 
if (!$hypervm) { 
    $hyperv = Get-ItemProperty hklm:\HARDWARE\DESCRIPTION\System -Name SystemBiosVersion 
    if ($hyperv -match "vrtual") { $hypervm = $true } 
} 
if (!$hypervm) { 
    $hyperv = Get-ChildItem HKLM:\SYSTEM\ControlSet001\Services 
    if (($hyperv -match "vmicheartbeat") -or ($hyperv -match "vmicvss") -or ($hyperv -match "vmicshutdown") -or ($hyperv -match "vmiexchange")) { $hypervm = $true } 
} 
if ($hypervm) { "This is a Hyper-V machine." } 

# VMWare Check Logic
$vmware = Get-ChildItem HKLM:\SYSTEM\ControlSet001\Services 
if (($vmware -match "vmdebug") -or ($vmware -match "vmmouse") -or ($vmware -match "VMTools") -or ($vmware -match "VMMEMCTL")) { $vmwarevm = $true } 
if ($vmwarevm) { "This is a VMWare machine." }
}

El chequeo térmico (ACPI Thermal Zone): la pieza más interesante

La consulta Get-WmiObject -Namespace root\wmi -Class MSAcpi_ThermalZoneTemperature intenta leer la propiedad CurrentTemperature de esa clase WMI, expresada en décimas de Kelvin por el controlador ACPI de la placa base. Esta clase solo existe si el firmware ACPI del sistema expone realmente una zona térmica — algo propio de hardware físico con sensores de temperatura. Hipervisores como VMware, VirtualBox o entornos de análisis automatizado (Cuckoo, Joe Sandbox) rara vez emulan esta tabla ACPI, porque no tiene ningún propósito funcional para una VM: el resultado es que la consulta WMI devuelve $null o lanza una excepción. El script se apoya en $ErrorActionPreference = "SilentlyContinue" precisamente para que, si la clase no existe, el error se silencie en vez de interrumpir la ejecución o generar una alerta visible — y usa esa ausencia de error (o el valor nulo) como señal de "esto es virtual". Es una técnica elegante porque no depende de buscar cadenas de texto delatoras (como "VMware" en un registro), sino de una propiedad física del hardware que es muy costosa de emular con fidelidad.

EncodedCommand: por qué su sola presencia ya es una señal

La invocación inicial registrada (Start "http://localhost:3000") llegó a través del parámetro -EncodedCommand de powershell.exe, que recibe el script codificado en Base64 sobre UTF-16LE. Es una técnica de ofuscación muy básica (no es cifrado, es solo una codificación reversible), pero sigue siendo efectiva contra inspección superficial de línea de comandos, ya que lo que aparece en la lista de procesos es una cadena Base64 ilegible a simple vista en vez del script en claro. Para un analista, el propio uso de -EncodedCommand es ya un indicador débil pero útil: el software legítimo rara vez necesita codificar así sus propios scripts, así que su sola presencia suele justificar mirar más de cerca.

Vale la pena notar el patrón común a todas las filas: ninguna de estas comprobaciones requiere privilegios elevados ni herramientas externas. Todo se hace con cmdlets nativos de PowerShell (Get-WmiObject, Get-ChildItem, Get-ItemProperty) sobre rutas de registro y namespaces WMI estándar — lo que hace que esta fase de reconocimiento sea tan silenciosa y barata de ejecutar, y por tanto tan habitual como primer paso antes de desplegar algo más ruidoso.

Es interesante que una sola función de 30 líneas cubra cinco técnicas de tres tácticas distintas. Esto es habitual en scripts de reconocimiento: no suelen tener una única finalidad, sino que combinan ejecución, evasión y descubrimiento en el mismo bloque porque el coste de hacerlo es mínimo y el beneficio (evitar ser analizado) es alto.

Recomendaciones de hardening y mitigación

  • Hardening de sandboxes de análisis: configurar los entornos de análisis dinámico (Cuckoo, CAPE Sandbox) para emular respuestas ficticias en consultas WMI sensibles como MSAcpi_ThermalZoneTemperature e inyectar claves de registro falsas que enmascaren los controladores de VMware/Hyper-V, de forma que una muestra que haga este chequeo "vea" hardware físico y continúe ejecutándose para poder ser analizada.
  • Restricción de PowerShell: desplegar Constrained Language Mode (CLM) mediante AppLocker o WDAC para impedir que código no firmado invoque clases WMI no autorizadas o acceda a rutas de registro sensibles sin pasar antes por una política de ejecución explícita.
  • Habilitar y centralizar Script Block Logging: sin Event ID 4104 activo, este análisis no habría sido posible, porque -EncodedCommand habría ocultado el contenido real del script en cualquier log que solo registrara la línea de comandos. Es, de lejos, la fuente de visibilidad más valiosa para detectar este tipo de actividad después del hecho.
  • Reglas de detección correlacionadas, no aisladas: una sola consulta a ControlSet001\Services no es sospechosa por sí sola, pero combinada con $ErrorActionPreference = "SilentlyContinue", una invocación vía -EncodedCommand y consultas WMI poco habituales en el namespace root\wmi, sí forma un patrón claro de reconocimiento anti-análisis — las reglas Sigma/Hayabusa deberían buscar esta combinación, no cada indicador por separado.
  • Threat hunting proactivo sobre Event ID 4104: buscar periódicamente, sobre el histórico de Script Block Logging, apariciones de cadenas como MSAcpi_ThermalZoneTemperature, vmicheartbeat o VMTools dentro de bloques de script, independientemente de si dispararon una alerta en su momento, ya que este tipo de chequeos tiende a reutilizarse sin cambios entre campañas distintas basadas en Nishang.
